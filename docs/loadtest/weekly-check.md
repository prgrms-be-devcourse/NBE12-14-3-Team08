# 주간 판정 스케줄러 부하 테스트 결과 (#93)

`HabitService.autoCheckAllActiveHabits`(매일 00:05, 측정 당시 코드이며 이후 묶음 방식으로 전환하며 제거)가 습관 수에 따라 얼마나 오래 걸리고, 도는 동안 다른 요청에 어떤 영향을 주는지 측정했습니다.

## 요약

| | 현재 방식 (한 트랜잭션으로 전체 순회) | 개선안 (습관 100개씩 트랜잭션 분리) |
|---|---|---|
| 습관 3,000개 | **35.2초** (습관당 11.7ms) | **9.2초** (습관당 3.1ms) |
| 습관 5,000개 | **90.1초** (습관당 18.0ms) | **16.4초** (습관당 3.3ms) |
| 습관 10,000개 | **386.9초 (6분 27초)** (습관당 38.7ms) | **32.1초** (습관당 3.2ms) |
| 판정 중 일반 조회(잠금 없음) 평균 | 5,000개에서 **35,061ms** (평소 7ms) | 5,000개에서 **5.2ms** (평소 5.8ms) |
| 판정 중 습관 포기(행 잠금) 평균 | 5,000개에서 **33,734ms** | 5,000개에서 **9.2ms** |

1. **현재 방식은 습관 수가 늘수록 습관당 시간이 계속 늘어납니다.** 전체 시간이 제곱에 가깝게 증가합니다. (1,000개 6.2ms → 3,000개 11.7ms → 5,000개 18.0ms → 10,000개 38.7ms)
2. **판정이 도는 동안 잠금과 무관한 요청도 느려지고 실패합니다.** 판정이 DB 연결을 오래 쥐는 동안, 습관 행 잠금에 막힌 요청이 연결을 붙잡고 있다가 연결 풀(10개)이 고갈됩니다. 이때 응답이 서버 오류(500)가 아니라 **401**로 나갑니다.
3. **습관을 100개씩 나눠 트랜잭션을 만들면 습관당 시간이 규모와 무관하게 약 3ms로 일정하고, 판정 중 다른 요청에 영향이 거의 없습니다.** 판정 결과(습관, 벌칙, 인증 상태)는 한 트랜잭션으로 돌렸을 때와 완전히 같습니다.

## 시나리오

### 데이터 (`loadtest/weekly-check/seed.sql`)
- 습관 10개 = 그룹 1개(회원 10명이 습관 1개씩). 습관 수 1,000 / 3,000 / 5,000 / 10,000.
- 그룹의 70%는 14일 전 생성(오늘이 마감 요일), 30%는 17일 전 생성(마감 요일이 3일 전이라 검토 유예가 지남)
- 그룹 안 10명의 인증: 6명은 승인 3건(통과), 3명은 승인 1건(부족으로 **실패**), 1명은 대기 3건(유예가 남은 그룹은 판정 보류, 지난 그룹은 **자동 승인**)
- 그 결과 습관의 약 30%가 실패 처리되어 벌칙이 만들어지고, 약 3%의 인증이 자동 승인됩니다.

### 실행 (`k6/weekly-check.js`)
- 시작 10초 뒤 판정을 **한 번** 실행합니다. (`loadtest` 프로파일 전용 `POST /loadtest/weekly-check/run`)
- 판정이 도는 동안 두 가지 요청을 계속 보냅니다.
  - **일반 조회**: 초당 20건의 습관 상세 조회 (`GET /api/habits/{id}`, 행 잠금을 쓰지 않음)
  - **습관 포기**: 초당 5건의 `POST /api/habits/fail/{id}` (판정과 같은 습관 행을 잠그는 요청)
- 판정이 시작·종료된 시각을 기록해, 요청을 **시작 시각 기준으로** "판정 중"과 "판정 밖"으로 나눠 집계합니다. (`analyze.mjs`)
- 회원 로그인(BCrypt) 대신 같은 비밀키로 토큰을 직접 만들어 씁니다. (`k6/lib/jwt.js`)

### 연결 풀 고갈과 오류 응답 (한 트랜잭션 방식)
- 앱 로그에 `HikariPool-1 - Connection is not available, request timed out after 30000ms (total=10, active=10, idle=0, waiting=189)`가 **1,744건** 남았습니다. 연결 10개가 모두 사용 중이고 요청 189개가 대기했습니다.
- 일반 조회 응답이 30초(`30006ms`) 근처에 몰리는 이유가 이 연결 대기 시간 초과입니다.
- 판정 중 일반 조회에서 **401**이 대량으로 나왔습니다. (3,000개: 43건, 5,000개: 300건. 습관 포기 요청에서도 13건, 80건) 1,000개에서는 401이 없었고(지연만 증가), 3,000개부터 풀이 고갈되며 나타났습니다. 100개씩 나눈 방식에서는 1,000 / 3,000 / 5,000 / 10,000개 모두 401이 한 건도 없었습니다.
- 5,000개에서는 k6 요청 시간 초과(60초)도 9건 있었습니다.

## 원인

판정 실행 중 스레드 덤프를 여러 번 떠 보니 시간 대부분이 Hibernate의 **자동 플러시(dirty checking)** 안에 있었습니다 (`DefaultAutoFlushEventListener.onAutoFlush` → `prepareEntityFlushes` → `Cascade`).

- `autoCheckAllActiveHabits`는 한 트랜잭션 안에서 습관을 하나씩 판정하며 인증 개수를 세는 쿼리를 실행합니다.
- 쿼리를 실행하기 전에 Hibernate가 영속성 컨텍스트에 쌓인 모든 엔티티의 변경 여부를 검사합니다. 습관, 그룹 멤버, 그룹이 계속 쌓이므로 **쿼리 한 번의 비용이 처리한 습관 수에 비례**하고, 전체는 제곱에 가깝게 늘어납니다.
- 이 트랜잭션이 연결 하나를 판정이 끝날 때까지 쥐고, 습관 행 잠금도 끝까지 쥡니다. 같은 행을 건드리는 요청(습관 포기)이 잠금에 막힌 채 연결을 붙잡으면 풀 10개가 금방 고갈됩니다.

## 개선안: 습관을 묶음으로 나눠 트랜잭션 분리

`HabitService.checkWeeklyChunk(habitIds)`를 추가했습니다. 습관 id 목록을 100개씩 나눠 묶음마다 별도 트랜잭션으로 판정합니다. 판정 로직은 그대로입니다. 이 개선은 `HabitWeeklyCheckScheduler`로 스케줄러에 적용했습니다. (아래 "적용 후 확인" 참고)

- 영속성 컨텍스트가 묶음마다 새로 시작되어 플러시 비용이 묶음 크기로 한정됩니다.
- 잠금과 연결을 묶음 시간(약 0.3초)만 쥡니다.
- 묶음 크기 25와 100을 3,000개에서 비교했을 때 8.7초와 9.1초로 차이가 거의 없었습니다. 묶음 크기보다 "나눈다"는 사실이 핵심입니다. (이 비교는 크기 두 가지만 확인했습니다.)

### 판정 결과가 같은지 확인
같은 시드에서 한 트랜잭션, 100개씩, 7개씩으로 판정한 뒤 **습관, 벌칙, 인증 상태 전체의 요약값(md5)**을 비교했습니다. 3가지 모두 일치했습니다. (습관 2,000개: 실패 600, 벌칙 600, 승인된 인증 4,380, 대기 420)

## 적용 후 확인 (스케줄러 전환)

`autoCheckAllActiveHabits`(한 트랜잭션)를 없애고, 스케줄러를 `HabitWeeklyCheckScheduler`로 옮겼습니다. 매일 00시 05분에 활성 습관 id를 조회해 100개씩 `checkWeeklyChunk`를 호출합니다. (묶음 크기: `app.habit.weekly-check.chunk-size`, 기본 100)

- **묶음 단위 오류 격리**: 한 묶음이 실패하면 그 묶음을 습관별로 다시 판정하고 문제가 된 습관만 건너뜁니다. 건너뛴 습관은 경고 로그에 남습니다. 기존에는 한 습관의 예외가 전체를 롤백했습니다. 판정은 다시 실행해도 결과가 같습니다. (이미 실패한 습관은 `ALREADY_FAILED`)
- **진행 로그**: `주간 판정을 마쳤습니다. 습관 N개, 묶음 M개, X ms`
- **비교 기준선 유지**: 측정용 컨트롤러의 `mode=single`은 `checkWeeklyChunk`에 전체 id를 한 번에 넘겨 개선 전 방식(한 트랜잭션)을 그대로 재현하고, `mode=chunked`는 실제 `HabitWeeklyCheckScheduler`를 호출합니다.

실제 스케줄러 클래스로 다시 측정한 결과입니다.

| 습관 수 | 방식 | 소요 시간 | 판정 중 일반 조회 평균 | 판정 중 습관 포기 평균 |
|---|---|---|---|---|
| 3,000 | 한 트랜잭션 (개선 전) | 35.6초 | - | - |
| 3,000 | `HabitWeeklyCheckScheduler` | **9.4초** | - | - |
| 5,000 | 한 트랜잭션 (개선 전, 앞의 측정) | 90.1초 | 35,061ms | 33,734ms |
| 5,000 | `HabitWeeklyCheckScheduler` | **17.0초** | **5.5ms** | **27.7ms** |

- 3,000개에서 두 방식의 최종 상태 요약값(md5)이 같습니다. (실패 900, 벌칙 900, 승인된 인증 6,570)
- 5,000개 판정 중 습관 포기 요청은 평균 27.7ms, p95 196ms로, 앞의 묶음 측정(평균 9.2ms)보다 약간 높았습니다. 한 번씩만 측정해 노이즈와 구분하지 못했습니다.
- 습관 포기 요청이 판정 중인 묶음의 행과 겹치면 그 묶음이 끝날 때까지(약 0.3초) 기다립니다. 기존에는 전체가 끝날 때까지(수십 초~분) 기다렸습니다.

## 해석할 때 주의할 점
- **풀 고갈의 직접 원인은 추정입니다.** 판정 중 습관 포기 요청이 잠금에 막힌 채 연결을 붙잡아 풀이 고갈된다고 보지만, 습관 포기 요청 없이 일반 조회만 보낸 실행으로 따로 확인하지는 않았습니다. (일반 조회가 느려진 시점과 풀 로그 `active=10, waiting=189`가 일치합니다.)
- **측정 중 습관 포기 요청이 일부 습관을 직접 실패 처리**합니다. 그래서 `failedHabits`, `penaltiesCreated`는 판정만의 결과가 아니며, 결과 동일성 검증은 요청이 섞이지 않은 별도 실행으로 했습니다.
- **웹 요청 안에서 돌리면 효과가 사라집니다.** Open Session In View(기본 켜짐) 때문에 요청 하나가 영속성 컨텍스트를 끝까지 공유해서, 트랜잭션을 나눠도 엔티티가 계속 쌓입니다. 측정 트리거는 실제 스케줄러와 같은 조건이 되도록 별도 스레드에서 실행합니다.
- 힙 사용량은 GC 시점에 좌우되어 두 방식의 차이를 결론으로 삼지 않았습니다.
- 한 대의 노트북에서 측정했고, 각 케이스를 한 번씩만 실행했습니다. 수치는 추세 확인용입니다.
- 실제 서비스에서는 스케줄러가 자정 5분에 도므로 동시 요청이 적을 수 있습니다. 다만 습관이 수천 개를 넘으면 판정만으로 연결 하나를 분 단위로 쥐게 됩니다.

## 후속 제안
1. ~~스케줄러를 묶음 단위 트랜잭션으로 바꾸기~~ → 적용했습니다. (`HabitWeeklyCheckScheduler`, 묶음 단위 오류 격리 포함)
2. 풀 고갈 시 응답이 401로 나가는 문제 확인. 인증 필터의 DB 조회 예외가 `/error` 디스패치에서 인증 거절로 바뀌는 것으로 추정하지만 **원인은 확인이 필요**합니다. 프론트가 401을 토큰 갱신 신호로 쓰므로 영향이 큽니다.
3. 판정 쿼리 줄이기: 습관당 4~5회인 SQL(잠금 조회, 지연 로딩, 대기·승인 카운트)을 습관 id 묶음 단위의 일괄 조회로 줄이면 묶음 방식에서 남은 3ms도 낮출 수 있습니다.

## 재현 방법

사전 조건: Docker 실행, `docker-compose.yml`의 `naegi-postgres` 컨테이너 실행.

```bash
# 1) 부하 테스트 전용 DB 만들기 (한 번만)
docker exec naegi-postgres psql -U naegi -d naegi -c "create database naegi_load"

# 2) 앱을 loadtest 프로파일로 실행 (처음 실행하면 테이블이 만들어집니다)
cd backend && ./gradlew bootRun --args="--spring.profiles.active=loadtest"

# 3) 한 케이스 실행: 시드 초기화 -> k6(판정 + 동시 요청) -> 구간별 집계
#    사용: run-case.sh <습관 수> <single|chunked> [묶음 크기=100] [프로브 시간(초)=60] [잠금 프로브 수=100]
loadtest/weekly-check/run-case.sh 3000 single 100 70 160
loadtest/weekly-check/run-case.sh 3000 chunked 100 40 60
```

- 판정 시간이 긴 케이스는 프로브 시간과 잠금 프로브 수를 늘립니다. (잠금 프로브는 초당 5건이라 `판정 시간(초) x 5`가 적당합니다.)
- 시드만 다시 넣으려면 `loadtest/weekly-check/seed.sh <습관 수>`. 판정은 실행할 때마다 습관을 FAILED로 바꾸므로 반복 측정 전에 반드시 다시 넣어야 합니다.
- Windows Git Bash에서는 `/k6/...` 경로가 변환되지 않도록 `MSYS_NO_PATHCONV=1`을 씁니다. (`run-case.sh`에 이미 포함)
- 원본 결과는 `k6/results/`에 저장되며 저장소에는 올리지 않습니다.
- 기존 `k6/load-test.js`는 토큰 없이 호출해 모두 401이 되므로 이 시나리오와 별개입니다.
