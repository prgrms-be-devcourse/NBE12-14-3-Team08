# 인증의 반응·댓글은 대상별 테이블 4개에 ON DELETE CASCADE FK를 걸고, 개수는 저장하지 않고 센다

멤버가 서로의 습관 인증과 벌칙 인증에 반응(하트)과 댓글을 남길 수 있게 하면서, 테이블을 `habit_verify_reaction`, `habit_verify_comment`, `penalty_verify_reaction`, `penalty_verify_comment` 네 개로 나누고 각각 인증과 방 멤버에 `ON DELETE CASCADE` FK를 걸기로 했다. 기존 `habit_verify`·`penalty_verify`에는 컬럼을 추가하지 않고, 하트·댓글 개수는 저장하지 않고 조회할 때 집계한다. 방 삭제·탈퇴·추방이 모두 직접 쿼리로 행을 지우는 구조라서, 정리 코드를 경로마다 두면 하나만 빠져도 삭제가 막힌다. DB가 인증이나 멤버를 지울 때 함께 지우게 하면 이를 코드로 기억할 필요가 없고, 개수를 저장하지 않으므로 동시에 눌러도 숫자가 어긋나지 않는다.

## 테이블 구조

습관 인증 기준이고, 벌칙 인증은 `habit_verify`를 `penalty_verify`로 바꾼 같은 구조다. 기존 테이블에는 컬럼을 추가하지 않는다. `id`, `create_date`, `modify_date`는 기존 `BaseEntity`가 주는 공통 컬럼이다.

```
habit_verify_reaction
  habit_verify_id  bigint NOT NULL  -> FK habit_verify(id) ON DELETE CASCADE
  group_member_id  bigint NOT NULL  -> FK group_member(id) ON DELETE CASCADE   (누른 사람)
  UNIQUE (habit_verify_id, group_member_id)                   (한 인증에 멤버당 하나)
  INDEX  (group_member_id)

habit_verify_comment
  habit_verify_id  bigint NOT NULL  -> FK habit_verify(id) ON DELETE CASCADE
  group_member_id  bigint NOT NULL  -> FK group_member(id) ON DELETE CASCADE   (쓴 사람)
  content          varchar(500) NOT NULL
  INDEX  (habit_verify_id, create_date)                       (목록 조회)
  INDEX  (group_member_id)
```

## 함께 정한 규칙

- **반응은 하트 하나**다. 한 인증에 방 멤버당 하나이고(유니크 `(인증, 방 멤버)`), 누른 상태로 만드는 요청(`PUT`)과 취소하는 요청(`DELETE`)을 나눈다. 같은 요청을 몇 번, 동시에 보내도 결과가 같다. 이모지 종류는 두지 않는다. 종류 컬럼과 집계가 복잡해지는 것에 비해 얻는 것이 작다.
- **본인 인증에는 하트를 누를 수 없다.** 본인이 누른 하트는 숫자만 부풀린다. 댓글은 본인 인증에도 쓸 수 있다.
- **댓글은 최대 500자**, 작성자만 수정·삭제하고 방장은 삭제만 할 수 있다. 대댓글은 두지 않고, 삭제하면 행을 실제로 지운다.
- **같은 방 멤버만 읽고 쓸 수 있다.** 읽기는 지금 인증 조회와 같이 방 소속이면 되고(나간 멤버 포함), **쓰기는 활동 중(`ACTIVE`)인 멤버이면서 방이 진행 중일 때만** 허용한다. 방이 종료되면 읽기만 가능하다.
- **승인된 인증에만 반응·댓글을 쓸 수 있다.** 방 메인 갤러리가 승인된 사진만 보여주고, 반려된 인증에 하트를 다는 것은 어색하기 때문이다. 검토중·반려 인증은 읽기만 가능하고, 승인 뒤에 반려로 바뀌어도 이미 달린 글은 지우지 않는다. 다만 이미 남긴 하트 취소와 내 댓글 수정·삭제는 인증 상태와 상관없이(진행 중인 방에서) 할 수 있다.
- **나간 멤버의 댓글은 "탈퇴한 멤버"로 표시한다.** 종료된 방에서 탈퇴한 멤버의 글은 남기되(멤버 행이 `LEFT`로 남는다), 탈퇴한 회원의 닉네임이 계속 노출되지 않게 한다. 작성자는 `member`가 아니라 `group_member`로 가리켜서 "이 방의 멤버"라는 조건을 FK로 보장하고 닉네임을 바로 조인한다.
- **방 메인 갤러리의 숫자는 습관 인증만** 보여준다. 갤러리에 벌칙 사진이 없기 때문이다. 호버에는 개수가 0이어도 `♥ 0`, `💬 0`을 보여준다.

## Considered Options

### 1. 대상마다 테이블을 따로 둘까, 하나의 다형 테이블을 쓸까

| | 대상별 4개 (선택) | 하나의 다형 테이블 2개 |
|---|---|---|
| 구조 | `habit_verify_*`, `penalty_verify_*`. 각각 FK | `reaction`, `comment`에 `target_type` + `target_id` |
| 무결성 | DB가 "존재하는 인증만 가리킨다"를 보장 | `target_id`가 어느 테이블의 번호인지 DB가 몰라 FK 불가. 서비스 코드가 매번 확인 |
| 코드량 | 엔티티·리포지토리가 두 벌. 서비스 로직은 공통 함수로 한 번만 작성 | 가장 적음 (공수 약 20% 절감) |

다형 테이블을 고르지 않은 이유는 **방 삭제** 때문이다. `GroupService.deleteGroup`은 `deleteGroupAndAllMembers`로 방과 멤버, 습관, 인증을 코드에서 순서대로 지운다. 다형 테이블은 FK가 없어서 이 코드에 댓글 정리를 빠뜨려도 오류가 나지 않고, 주인이 사라진 댓글이 조용히 남는다. 나중에 같은 번호의 인증이 생기면 엉뚱한 글이 붙을 수도 있다. 4개 테이블은 FK가 있어서 "존재하는 인증만 가리킨다"를 DB가 보장하고, `ON DELETE CASCADE`로 정리까지 맡긴다.

### 2. 개수를 컬럼으로 저장할까, 조회할 때 셀까

`habit_verify`에 `reaction_count`, `comment_count` 컬럼을 두는 안은 읽기가 가장 싸다. 하지만 여러 명이 동시에 누르면 갱신이 겹쳐 숫자가 틀어질 수 있고, 틀어지면 다시 세는 보정 로직이 따로 필요하다. 그래서 **저장하지 않고** 갤러리 한 페이지(수십 장)의 인증 id를 모아 `where <인증>_id in (...) group by`로 한 번에 센다. 갤러리 응답에는 `reactionCount`, `commentCount`, `reactedByMe`를 더하되, **요청에 `includeEngagement=true`를 보낼 때만** 채운다. 기존 응답 형태에 의존하는 호출자를 깨지 않기 위해서이고, 값이 없으면 필드를 응답에서 뺀다. 방 하나의 인증과 멤버 수가 작은 서비스라 집계 비용이 문제가 될 가능성이 낮다. 느려지면 그때 컬럼 저장으로 바꾸는 것은 가능하다(되돌리기 쉬운 쪽).

### 3. 지울 때 정리를 코드로 할까, DB에 맡길까

처음에는 삭제 쿼리마다 반응·댓글 삭제를 앞에 더하는 안(명시적 정리)을 생각했다. 구현하면서 **FK에 `ON DELETE CASCADE`를 거는 안**으로 바꿨다(엔티티의 `@OnDelete(CASCADE)`).

| | 코드로 정리 | DB CASCADE (선택) |
|---|---|---|
| 빠뜨릴 위험 | 삭제 경로 7개 쿼리마다 더해야 하고, 새 경로가 생기면 또 더해야 한다 | 없음. 인증·멤버 행이 지워지면 DB가 함께 지운다 |
| 기존 코드 | 삭제 서비스·쿼리를 고친다 | 기존 삭제 코드를 건드리지 않는다 |
| 단점 | 영속성 컨텍스트 flush 순서에 신경 써야 한다 | 지운 행이 영속성 컨텍스트에 남아 있을 수 있어 같은 트랜잭션에서 다시 읽을 때 주의 |

벌칙 인증만은 예외다. 행을 지우지 않고 상태만 되돌리므로 CASCADE가 일어나지 않아 코드로 지운다(아래).

## Consequences

- **벌칙 인증과의 관계(ADR 0001)**: 벌칙 인증 행은 지우지 않고 상태만 되돌린다. 그러면 옛 증빙에 달린 반응·댓글이 새 증빙 옆에 남는 문제가 생기므로, **벌칙 초기화와 제출 취소 때 그 인증의 반응·댓글도 함께 지운다.** 습관 인증은 반려 후 재제출해도 같은 행이라 반응·댓글을 유지한다. 이 정리는 `PenaltyVerifyResetService`가 기존 `cancelOrReset` 호출과 한 트랜잭션으로 묶어 처리하고, 권한·상태 검사에 실패하면 아무것도 지우지 않는다. 기존 `PenaltyVerifyService`는 바꾸지 않았다. 또 초기화가 하트·댓글을 지우는 순간에 새 하트·댓글이 들어오면 미제출 벌칙에 글이 남을 수 있어서(동시성 테스트에서 재현), 벌칙에 쓰기 전에 그 벌칙 행을 먼저 잠근다(`select ... for update`). 잠금 뒤에 상태를 읽으므로 초기화가 먼저 끝났다면 쓰기가 거절된다.
- **지우는 경로 3곳은 DB가 정리하고, 테스트로 확인한다.** 삭제 코드를 고치지 않아도 아래처럼 동작한다.
  - **방 삭제**(`deleteGroupAndAllMembers`): 인증과 멤버가 지워지면서 반응·댓글도 함께 지워진다.
  - **진행 중인 방에서 탈퇴·추방**(`deleteGroupMemberDataBulk` 후 멤버 행 삭제): 그 멤버의 인증에 달린 반응·댓글과, **그 멤버가 남의 인증에 쓴 반응·댓글**이 함께 지워진다. 그 멤버의 인증이 함께 지워지는 것과 같은 동작이다.
  - **종료된 방에서 탈퇴**(`leave()`, 멤버 행을 지우지 않고 `LEFT`로 남김): 반응·댓글을 그대로 둔다. 기록을 남기는 것이 종료된 방의 목적이다.
- **구현할 때 알아 둘 것**
  - 멤버 행 삭제는 저장 시점(flush)에 실행되므로, 같은 트랜잭션에서 지운 결과를 확인하려면 flush가 필요하다.
  - **댓글 길이를 명시한다.** 문자열 컬럼은 길이를 쓰지 않으면 255자로 만들어지므로 `@Column(length = 500)`과 요청 검증 `@Size(max = 500)`을 함께 둔다.
  - **하트는 DB가 중복을 걸러 낸다.** `insert ... on conflict do nothing`으로 넣어서 같은 사람이 동시에 눌러도 오류 없이 하나만 남는다. "있는지 확인 후 저장"은 그 사이에 끼어들면 유니크 제약 오류가 난다.
  - 두 인증이 같이 쓰는 요청·응답 DTO와 권한 규칙은 `verifyEngagement` 패키지(`EngagementRules`)에 한 번만 둔다. 엔티티·저장소·컨트롤러는 대상별로 둔다.
- **테이블은 JPA가 만든다**(`ddl-auto: update`). 운영에 올릴 때 별도 마이그레이션 도구는 없다. 지금 프로젝트의 방식을 그대로 따른다.
- **알림은 만들지 않는다.** 반응·댓글이 달려도 알려 주는 기능은 이번 범위가 아니다.
