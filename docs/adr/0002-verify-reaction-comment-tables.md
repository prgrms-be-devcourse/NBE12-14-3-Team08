# 인증의 반응·댓글은 대상별 테이블 4개에 FK를 걸고, 개수는 저장하지 않고 센다

멤버가 서로의 습관 인증과 벌칙 인증에 반응(하트)과 댓글을 남길 수 있게 하면서, 테이블을 `habit_verify_reaction`, `habit_verify_comment`, `penalty_verify_reaction`, `penalty_verify_comment` 네 개로 나누고 각각 인증과 방 멤버에 FK를 걸기로 했다. 기존 `habit_verify`·`penalty_verify`에는 컬럼을 추가하지 않고, 하트·댓글 개수는 저장하지 않고 조회할 때 집계한다. 방 삭제가 연관 데이터를 코드로 직접 지우는 구조라서 FK가 지우는 순서의 누락을 오류로 드러내 주고, 동시에 누르는 경우에도 숫자가 어긋나지 않기 때문이다.

## 테이블 구조

습관 인증 기준이고, 벌칙 인증은 `habit_verify`를 `penalty_verify`로 바꾼 같은 구조다. 기존 테이블에는 컬럼을 추가하지 않는다. `id`, `create_date`, `modify_date`는 기존 `BaseEntity`가 주는 공통 컬럼이다.

```
habit_verify_reaction
  habit_verify_id  bigint NOT NULL  -> FK habit_verify(id)
  group_member_id  bigint NOT NULL  -> FK group_member(id)     (누른 사람)
  UNIQUE (habit_verify_id, group_member_id)                   (한 인증에 멤버당 하나)
  INDEX  (group_member_id)

habit_verify_comment
  habit_verify_id  bigint NOT NULL  -> FK habit_verify(id)
  group_member_id  bigint NOT NULL  -> FK group_member(id)     (쓴 사람)
  content          varchar(500) NOT NULL
  INDEX  (habit_verify_id, create_date)                       (목록 조회)
  INDEX  (group_member_id)
```

## 함께 정한 규칙

- **반응은 하트 하나**다. 한 인증에 방 멤버당 하나이고(유니크 `(인증, 방 멤버)`), 다시 누르면 행을 지워 취소한다. 이모지 종류는 두지 않는다. 종류 컬럼과 집계가 복잡해지는 것에 비해 얻는 것이 작다.
- **본인 인증에는 하트를 누를 수 없다.** 본인이 누른 하트는 숫자만 부풀린다. 댓글은 본인 인증에도 쓸 수 있다.
- **댓글은 최대 500자**, 작성자만 수정·삭제하고 방장은 삭제만 할 수 있다. 대댓글은 두지 않고, 삭제하면 행을 실제로 지운다.
- **같은 방 멤버만 읽고 쓸 수 있다.** 읽기는 지금 인증 조회와 같이 방 소속이면 되고(나간 멤버 포함), **쓰기는 활동 중(`ACTIVE`)인 멤버이면서 방이 진행 중일 때만** 허용한다. 방이 종료되면 읽기만 가능하다.
- **승인된 인증에만 반응·댓글을 쓸 수 있다.** 방 메인 갤러리가 승인된 사진만 보여주고, 반려된 인증에 하트를 다는 것은 어색하기 때문이다. 검토중·반려 인증은 읽기만 가능하고, 승인 뒤에 반려로 바뀌어도 이미 달린 글은 지우지 않는다.
- **나간 멤버의 댓글은 "탈퇴한 멤버"로 표시한다.** 종료된 방에서 탈퇴한 멤버의 글은 남기되(멤버 행이 `LEFT`로 남는다), 탈퇴한 회원의 닉네임이 계속 노출되지 않게 한다. 작성자는 `member`가 아니라 `group_member`로 가리켜서 "이 방의 멤버"라는 조건을 FK로 보장하고 닉네임을 바로 조인한다.
- **방 메인 갤러리의 숫자는 습관 인증만** 보여준다. 갤러리에 벌칙 사진이 없기 때문이다. 호버에는 개수가 0이어도 `♥ 0`, `💬 0`을 보여준다.

## Considered Options

### 1. 대상마다 테이블을 따로 둘까, 하나의 다형 테이블을 쓸까

| | 대상별 4개 (선택) | 하나의 다형 테이블 2개 |
|---|---|---|
| 구조 | `habit_verify_*`, `penalty_verify_*`. 각각 FK | `reaction`, `comment`에 `target_type` + `target_id` |
| 무결성 | DB가 "존재하는 인증만 가리킨다"를 보장 | `target_id`가 어느 테이블의 번호인지 DB가 몰라 FK 불가. 서비스 코드가 매번 확인 |
| 코드량 | 엔티티·리포지토리가 두 벌. 서비스 로직은 공통 함수로 한 번만 작성 | 가장 적음 (공수 약 20% 절감) |

다형 테이블을 고르지 않은 이유는 **방 삭제** 때문이다. `GroupService.deleteGroup`은 `deleteGroupAndAllMembers`로 방과 멤버, 습관, 인증을 코드에서 순서대로 지운다. 다형 테이블은 FK가 없어서 이 코드에 댓글 정리를 빠뜨려도 오류가 나지 않고, 주인이 사라진 댓글이 조용히 남는다. 나중에 같은 번호의 인증이 생기면 엉뚱한 글이 붙을 수도 있다. 4개 테이블은 정리를 빠뜨리면 FK 위반으로 바로 드러난다.

### 2. 개수를 컬럼으로 저장할까, 조회할 때 셀까

`habit_verify`에 `reaction_count`, `comment_count` 컬럼을 두는 안은 읽기가 가장 싸다. 하지만 여러 명이 동시에 누르면 갱신이 겹쳐 숫자가 틀어질 수 있고, 틀어지면 다시 세는 보정 로직이 따로 필요하다. 그래서 **저장하지 않고** 갤러리 한 페이지(수십 장)의 인증 id를 모아 `where <인증>_id in (...) group by`로 한 번에 센다. 응답에는 `reactionCount`, `commentCount`, `reactedByMe`를 더한다. 방 하나의 인증과 멤버 수가 작은 서비스라 집계 비용이 문제가 될 가능성이 낮다. 느려지면 그때 컬럼 저장으로 바꾸는 것은 가능하다(되돌리기 쉬운 쪽).

## Consequences

- **벌칙 인증과의 관계(ADR 0001)**: 벌칙 인증 행은 지우지 않고 상태만 되돌린다. 그러면 옛 증빙에 달린 반응·댓글이 새 증빙 옆에 남는 문제가 생기므로, **벌칙 초기화와 제출 취소 때 그 인증의 반응·댓글도 함께 지운다.** 습관 인증은 반려 후 재제출해도 같은 행이라 반응·댓글을 유지한다. (구현 이슈에서 확정하고, 바뀌면 이 문서를 갱신한다.)
- **지우는 경로 3곳을 모두 정리해야 한다.** FK 때문에 하나라도 빠뜨리면 삭제가 막힌다. 새 테이블을 더 만들면 이 코드도 함께 고쳐야 한다.
  - **방 삭제**(`deleteGroupAndAllMembers`): 반응·댓글을 인증보다 먼저 지운다.
  - **진행 중인 방에서 탈퇴·추방**(`deleteGroupMemberDataBulk` 후 멤버 행 삭제): 그 멤버의 인증에 달린 반응·댓글과, **그 멤버가 남의 인증에 쓴 반응·댓글**을 함께 지운다. 멤버 행을 지우려면 그 멤버를 가리키는 FK가 없어야 하기 때문이다. 그 멤버의 인증이 함께 지워지는 것과 같은 동작이다.
  - **종료된 방에서 탈퇴**(`leave()`, 멤버 행을 지우지 않고 `LEFT`로 남김): 반응·댓글을 그대로 둔다. 기록을 남기는 것이 종료된 방의 목적이다.
- **구현할 때 빠뜨리기 쉬운 것** (코드를 읽어 확인한 내용)
  - **JPA 연쇄 삭제가 없다.** 엔티티에 `@OneToMany`·`cascade`가 없고 모든 삭제가 직접 쿼리라서, 새 테이블 정리를 인증·습관·멤버를 지우는 쿼리마다 앞에 더해야 한다(`deleteByHabitIds`, `deleteHabitVerifiesByGroupId`, `deleteByGroupMemberId`, `deletePenaltyVerifiesByGroupId`, `deleteByIds`, `deleteHabitsByGroupId`, `deleteGroupMembersByGroupId`). 영속성 컨텍스트를 비우는 옵션이 섞여 있어 기존과 같은 순서·flush 패턴을 따른다.
  - **벌칙 초기화·제출 취소(`cancelOrReset`)는 행을 지우지 않고 증빙만 비운다.** 그래서 엔티티 메서드가 아니라 서비스에서 반응·댓글 삭제를 직접 호출해야 한다.
  - **댓글 길이를 명시한다.** 문자열 컬럼은 길이를 쓰지 않으면 255자로 만들어지므로 `@Column(length = 500)`과 요청 검증 `@Size(max = 500)`을 함께 둔다.
  - **하트 토글은 동시에 눌러도 오류가 나지 않게 한다.** "있는지 확인 후 저장" 사이에 끼어들면 유니크 제약 오류가 나므로 오류를 잡아 멱등하게 처리한다.
  - 삭제와 작성이 동시에 일어나도 FK 때문에 고아 댓글은 남지 않고 한쪽이 오류로 끝난다.
- **테이블은 JPA가 만든다**(`ddl-auto: update`). 운영에 올릴 때 별도 마이그레이션 도구는 없다. 지금 프로젝트의 방식을 그대로 따른다.
- **알림은 만들지 않는다.** 반응·댓글이 달려도 알려 주는 기능은 이번 범위가 아니다.
